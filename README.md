# 微信 ClawBot · cortico-world-wechat-claw

通过微信 ClawBot（iLink）和 Coopanion 桌宠一对一聊天。**文字、图片、文件双向收发。**

文件这条路是这么走的：微信里发来的东西**落在桌宠自己的工作区里**（`wechat-inbox/`），所以它读得到、
改得了、也能改完再发回去；反过来，**能发到微信的只有工作区里的文件**——工作区外面（凭据、系统目录、
浏览器数据）不在范围里，模型再被说服也上传不出去。

这是独立开发的实现，不复用 `cortico-world-clawbot` 的代码。协议形状对齐腾讯官方
[`@tencent-weixin/openclaw-weixin`](https://www.npmjs.com/package/@tencent-weixin/openclaw-weixin)
2.4.10 与它的[后端协议文档](https://github.com/Tencent/openclaw-weixin/blob/main/docs/protocol_zh_CN.md)。

## 和现成 Claw 插件的差别

| | 现成 `cortico-world-clawbot` 0.1.0 | 这个扩展 |
|---|---|---|
| 文本收发 | 支持 | 支持 |
| 收图片 | 只显示 `[图片]` 占位 | 解密落到桌宠工作区的 `wechat-inbox/images/`，路径进上下文，模型支持图片时作为附件到达 |
| 发图片 | 不支持 | `wechat_send_image`：加密上传到微信 CDN 再发；**路径必须在工作区内** |
| 收文件 | 只显示 `[文件 名字]` 占位 | 解密落到 `wechat-inbox/files/`，保留对方给的原文名；她读得到、改得了，也能原样发回去 |
| 发文件 | 不支持 | `wechat_send_file`：同上，带原文件名与明文长度；同样只限工作区 |
| 上传来源 | —— | 只限工作区＋收件目录＋`sendExtraDirs`；先 `realpath` 再判定，`..` 与符号链接都绕不出去 |
| 语音 | 占位 | 保留服务端转写。SILK 转成 WAV 后落到 `wechat-inbox/voices/`，Provider 支持时一并附上 |
| 长文本 | 超 4000 字被拒 | 自动切成多条发送，优先在段落与句号处断开 |
| 出站视频 | 不支持 | 按 MIME 走视频通道，微信里显示成视频而不是附件 |
| 入站超限 | 无区分 | 超限、缺参数、下载失败三种原因分别措辞 |
| 视频 | 占位 | 可选下载（默认关）；Provider 接受时直接附视频，否则按原逻辑抽帧拼图，失败写明原因 |
| 网络出口 | inherit / direct / proxy | 相同，且把「配置要的出口做不到」如实报出来 |
| 令牌失效 | 直接断开并清凭据 | 按官方约定暂停一小时后重试，只有 HTTP 401/403 才判定会话过期 |
| 绑定面板 | 有 | 有，走内建 UI 原语，带二维码、扫码状态、验证码输入 |

## 工具

| 工具 | 作用 |
|---|---|
| `wechat_send` | 回复最近一条微信消息；只能发给刚发消息的人，单条上限 4000 字 |
| `wechat_send_image` | 把工作区里的一张图发到微信，可带一句说明；工作区外的路径直接拒绝 |
| `wechat_send_file` | 把工作区里的一个文件发到微信，可带一句说明；同样只限工作区 |
| `wechat_send_voice` | 把工作区或微信收件目录中的 WAV、MP3、SILK v3 发成 MP3 音频文件卡片，失败时补发文字 |
| `wechat_speak` | 启用微信 TTS 后，将指定文字合成音频发到微信，失败时补发原文 |
| `wechat_status` | 连接、账号、最近消息、错误、持有多少条会话令牌，以及工作区/收件目录/允许发送的目录 |
| `wechat_events` | 按类型和时间查已归档的微信事件 |

| 事件 | 作用 |
|---|---|
| `wechat-claw.message` | 一条微信私聊消息；媒体路径在正文里，Provider 支持的媒体与文档作为附件随事件到达 |
| `wechat-claw.link` | 绑定成功或会话过期 |

## 安装

设置 → 扩展 → 安装本地扩展，选这个目录；重启 Coopanion。然后在 World 页启用「微信 ClawBot」。

```bash
cd %APPDATA%\Coopanion\extensions
corepack pnpm add "<本地包目录，绝对路径，例如 E:\WorkShop\...\cortico-world-wechat-claw>"
```

这条说的是**安装本地包**要填包所在目录的绝对路径，与「发出去的文件路径」无关。

装好不等于启用：配置段默认 `enabled: false`，要去 World 总览激活。

## 绑定

1. 打开「连接与工具」，在微信绑定区域点「生成二维码」。
2. 用手机微信扫码；二维码打不开时复制面板里的链接。
3. 手机要求输入数字时，在面板的验证码框里填写并提交。

绑定成功后重启不需要重新扫码，直到会话过期。一个微信号只能绑定一个 ClawBot 客户端；换号或解绑请在微信里操作。

## 配置

配置段是 `worlds.wechat-claw`。配置页按「消息投递与回复」「附件收发」「图片与视频」「微信网络」分组，最后的「调试」放置原生进度卡和原生语音条。语音合成服务在「连接与工具」的「TTS 设置」中配置。

| 键 | 默认 | 说明 |
|---|---|---|
| `enabled` | `false` | 是否挂载本 World；打开后尝试用已保存的凭据连接 |
| `networkMode` | `inherit` | `inherit` 跟随 Coopanion 的代理；`direct` 直连；`proxy` 用 `proxyUrl` |
| `proxyUrl` | 空 | `proxy` 模式的 HTTP/HTTPS 代理，例如 `http://127.0.0.1:7890` |
| `forceIpv4` | `false` | `direct`/`proxy` 下强制 IPv4 |
| `inboundTrigger` | `debounce` | 微信消息投递方式。保存后对后续入站事件生效 |
| `receiveImages` | `true` | 收图时下载并交给模型 |
| `receiveFiles` | `true` | 收文件时下载，Provider 接受实际 MIME 时附在消息中 |
| `receiveVideos` | `false` | 收微信视频消息时下载（体积大，默认关）；原生理解也需开启 |
| `receiveVoices` | `true` | 下载语音并将 SILK 转成 WAV |
| `maxInboundMediaMb` | `20` | 单条入站与出站媒体上限。转换后的 WAV 超限时保留 SILK 原件 |
| `inboxDir` | 空 | 收件目录。留空＝桌宠工作区下的 `wechat-inbox`；相对路径按工作区解析。改完要重启 |
| `sendExtraDirs` | 空 | 额外允许发到微信的目录，一行一个（分号、逗号也行）。留空时只有工作区（与收件目录）能发 |
| `ffmpegSource` | `auto` | 视频抽帧用哪份 ffmpeg：`auto` 先 PATH 再用面板装的那份、`path` 只用 PATH、`off` 不抽帧 |
| `videoFrames` | `4` | 每条视频抽几帧（上限 9），抽完拼成一张图；0 表示不抽 |
| `imageMaxMb` | `16` | 单图体积上限，超了先压缩，压不了就不附 |
| `imageMaxEdge` | `4096` | 单图最长边上限，超了先缩小 |
| `imageMaxCount` | `10` | 一次事件投递最多附几张图 |
| `ffmpegProxyUrl` | 空 | 下载 ffmpeg 用的代理；留空直连（不继承只给模型用的那条代理） |
| `segmentEnabled` | `true` | 分段发送：一次回复拆成多条微信消息 |
| `segmentPace` | `1` | 聊天节奏，0～10；越大停顿越久，0 不等待 |
| `segmentMaxParts` | `8` | 语义段数达到此阈值就恢复完整原文，仅按 4000 字上限分条。0 使用默认值，旧配置大于 8 时按 8 执行 |
| `segmentMaxTotalSec` | `30` | 累计等待上限，到点不再等但剩下的照常发完 |
| `nativeVoiceEnabled` | `false` | 「试用微信原生语音条」开关，保存即时生效 |
| `ttsEnabled` | `false` | 启用 `wechat_speak` |
| `ttsProtocol` | `openai` | `openai` 为 OpenAI 兼容接口，`gpt-sovits` 为大肥鱼 GPT-SoVITS 公开语音接口 |
| `ttsBaseUrl` | 空 | TTS 服务地址 |
| `ttsModel` | 空 | TTS 模型名 |
| `ttsVoice` | 空 | TTS 声音名 |
| `ttsSpeed` | `1` | TTS 语速，范围 0.25–4 |

`bot_token`、同步游标和 `context_token` 都在 `<dataDir>/wechat-claw/`，不进配置、不进日志、不进事件 `meta.raw`。
**它们在工作区外面，所以发不出去**——`wechat_send_image` / `wechat_send_file` 只接受工作区内的路径（见下）。

## 收来的文件落在哪

收到的图片、文件、视频、语音直接落进**桌宠工作区的收件目录**：

```
<工作区>/wechat-inbox/
├── images/     wx-image-20261108-144219.png
├── files/      报告-20261108-144219.pdf     ← 原文名在前，时间戳在后
├── videos/     wx-video-20261108-144219.mp4
├── voices/     wx-voice-20261108-144219.wav
└── .derived/   压缩后的图、视频拼图（中间产物）
```

工作区是哪个目录，按框架自己的解析顺序猜：`config.json` 的 `paths.memory` 优先，其次探测
`<部署目录>/workspace`（Coopanion 的 Coo 用这个），再退到 `memory`。`wechat_status` 会如实报出
实际用的 `workspace`、`inbox` 和允许发送的目录，`wechat-claw` 的环境提示词里也写着收件目录的绝对路径。

放在这里而不是插件自己的数据目录，是因为**桌宠要伸手去够**：它读得到、改得了、也能原样发回去。
文件名保留对方给的原文名，撞名时退到 `-2`、`-3`，从不覆盖已有文件。

工作区如果是一个 Git 仓库（Coopanion 的 Coo 就是），启动时会把 `wechat-inbox/` 追加进工作区的
`.gitignore`——十几 MB 的视频进版本历史没有意义。**只在 `.gitignore` 已存在时追加**，且幂等。

## 发出去只能取工作区里的文件

这是本扩展的安全边界：`wechat_send_image` 和 `wechat_send_file` 只接受**工作区、收件目录，
以及 `sendExtraDirs` 里额外放行的目录**内的路径。

理由很实在：模型能被说服。原来把本机任意路径交给它，等于把 `auth.json`、`context-tokens.json`、
浏览器 cookie 一起交出去。现在这些文件在工作区外面，边界一挡就拿不到了。

- 判断前先做 `realpath`，所以 `..` 和符号链接都绕不出去。
- 拒绝时回执会列出允许的目录和收件目录，模型照着调整路径即可，不需要反复试错。
- 确实要发工作区以外的素材，把目录写进 `sendExtraDirs`；每加一个，能发出去的东西就多一片。

收来的文件在工作区里，所以「收到 → 改 → 发回」这条路是通的，不需要额外放行任何目录。

## 分段发送

`wechat_send` 在分段前转换美元符号包裹的 LaTeX 公式，并把列表项的缩进续文合并到对应标题行。公式尽量转成 Unicode，复杂命令保留可读文本。代码围栏、行内代码与普通金额保留。列表项之间的换行继续参与语义分段。

微信里一次吐一大段不像人说话。打开分段发送后，一次回复会拆成几条，一条一条发，条与条之间停顿。

**拆分只算一次**，不会拆两次：

| 文本里有 | 按什么拆 | 分隔符 |
|---|---|---|
| 换行 `\n` | 只按换行 | 删掉 |
| 没有换行，有句号 `。．.` | 只按句号 | 删掉 |
| 都没有，有 `！？!?…～~` 或 ASCII 省略号 | 只按这些 | **保留** |
| 都没有 | 整条发 | —— |

换行和句号同时出现时（「三层：\n第一。\n第二。」），按换行拆完就结束，**不会再多拆一次**；
但紧挨换行的段尾句号会一并去掉，所以发出去是「第一」「第二」，段内的句号保留。

**为什么删句号**：微信里带句号显得生硬，像在写公文，真人不这么打字。`！？…～` 留着，因为那是语气。

**连续符号完整保留**：`~♡`、`……`、`......`、`？！`、`!!!` 等只在整串末尾切一次，尾随的爱心、emoji 和右引号跟着前一句。符号之间只有空格时也一起保留，例如 `好呀~♡ ......再说` 会发成「好呀~♡ ......」「再说」。

**ASCII `.` 有额外保护**：单个点只在后面跟空白或位于结尾时才当句号。所以 `3.14`、`docs.nonebot.dev`、`report.2026.11.md` 不会被切坏。连续两个及以上的点按省略号保留，换行前也不会删掉；`../`、`..\` 这类路径片段不参与省略号分段。

语义段数**达到** `segmentMaxParts` 时取消语义分段，保留预处理后文本的换行和标点。按语义拆出的多条消息会用尽或超出剩余额度时，同样发送预处理后的完整文本。超过微信单条 4000 字时仍按长度分条。累计等待超过 `segmentMaxTotalSec` 后，其余消息连续发送。

扩展按复现中的 10 条为每个 `context_token` 设置本地发送上限。文字、媒体和附件说明每成功发出一条都计入同一额度，重启后保留计数。发送前会核对剩余条数，完整内容发不下时会提前拒绝这次调用。收到 `ret=-2 prepare failed` 时会停用这次使用的凭据，报告已发送条数，等对方发来带新凭据的消息再恢复回复。

「聊天节奏」控制每条消息发送前的停顿，默认 1：

| 每个语义段的字数 | 停顿 |
|---|---|
| 0～20 | 立即发送 |
| 21～80 | 0.6 秒 × 聊天节奏 |
| 81～300 | 1.4 秒 × 聊天节奏 |
| 超过 300 | 视作未能断句，立即发送，包括按 4000 字拆出的各条 |

达到分段阈值或关闭分段时不等待。旧的 `segmentDelayMode`、`segmentDelayFixedSec`、`segmentDelayMinSec`、`segmentDelayMaxSec` 不再使用，已有配置可删除；没有 `segmentPace` 时使用默认值 1。

不想要就在配置页关掉「分段发送」。

## 出站音频与 TTS

`wechat_send_voice` 接收工作区或微信收件目录内的绝对路径。默认上传 MP3 音频文件卡片（`media_type: 3`、`item.type: 4`）。已有 MP3 原样上传，WAV（单声道或立体声 PCM/浮点）与 SILK v3 在本地转成 MP3，无需 ffmpeg。消息里的 CDN 引用取自实际上传响应头 `x-encrypted-param`。

也可用 `blob` 参数发送 Core 已保存的音频，接受 `log:`、`mem:` 句柄或 `[blob …]` 回执行。例如先调用 `sovits_speak(silent: true)`，再把回执里的音频句柄传给 `wechat_send_voice`。每次调用在 `path` 和 `blob` 中选一项，仍需可用的微信回复额度。

打开「试用微信原生语音条」后优先将音频编码为 24 kHz、16-bit、单声道腾讯 SILK，用 `media_type: 4` 上传并发送 `type: 3` 的 `voice_item`。接口接收后的显示、播放以手机端为准。原生转码或上传失败、发送被明确拒绝时，自动改发 MP3。

音频处理、上传或明确发送失败时，`wechat_send_voice` 补发 `fallback_text` 提供的转写或说明，留空时发送失败提示。`wechat_speak` 在合成或音频发送失败时补发原文。补发文字使用同一回复凭据和剩余额度。凭据失效、耗尽、工具取消或发送结果不确定时，工具返回失败原因。

打开「连接与工具」里的「TTS 设置」，在同一个抽屉里填写开关、服务地址、模型、声音、语速和 API Key。普通设置与 API Key 分别保存，保存后即时生效。也可为部署设置 `WECHAT_CLAW_TTS_API_KEY`。`wechat_speak(text)` 将文字提交至该服务生成临时 MP3，走同一条音频发送路径，随后清理临时文件。

使用硅基流动时，保存 API Key 后可点「获取模型」，列表只显示账号可见且官方文档确认支持合成的型号。选好模型再点「获取音色」，即可选择官方预置或账号中属于该模型的自定义音色。其他服务仍可手动填写。服务地址也接受末尾为 `/chat/completions` 的兼容接口地址。

使用大肥鱼 GPT-SoVITS 时，先在服务端打开「开放本机语音接口」，再在这里点击「发现本机与局域网服务」。单项结果会直接填入配置，多项结果可从下拉框选择。按「保存设置」生效。大肥鱼默认只监听本机，其他设备需要通过局域网地址提供该公开接口。发现仅在点击按钮后检查本机及当前私有 IPv4 网段的 `9880`、`9883` 端口，也会检查已填写的本机或私网地址。自定义地址或需要令牌的服务可以手动添加，密钥按服务地址单独保存。模型与音色留空时使用服务默认值。合成通过 HTTP `/audio/speech` 返回 WAV，再转成微信音频文件，全程无需调用其他 World 工具。

## 视频抽帧

入站文件按可确认的文件头识别 PDF、图片、音频和视频容器；无法确认时使用文件名或微信语音编码提供的类型。每次收件都调用宿主的 `modelFacts.accepts(实际 MIME)`，随当前模型、Provider 协议和输入开关变化。支持时通过事件 `blobs` 提交实际字节、MIME 与文件名；未知类型不会冒充支持的格式。

可调用 `wechat_status`，传入 `{"mimes":["video/mp4","audio/wav","application/pdf"]}` 查看 `inputSupport`。`accepted` 是当前 Provider 的类型判断，`error` 表示查询失败；`receive` 是本扩展的下载开关。`lastInboundAttachments` 与事件的 `meta.media` 记录每份文件交给 Core 时的结果：`native` 为原样附件，`frames` 为视频拼图，`omitted` 为未附，原因在 `notes`。这不代表上游已经成功理解文件；字节、总请求大小等仍由 Provider 和上游校验。

OpenCode 原生 Gemini 会将支持的音频、视频、PDF 等附件编码到请求的 `contents[].parts[].inlineData`。请先在 OpenCode 获取模型列表以更新格式声明，并确认所需输入类型未关闭。微信视频消息还需在本扩展打开「收视频」，文件通道发送的视频由「收文件」控制。微信 SILK 转码成功后使用 `audio/wav` 判断附件支持，服务端转写仍会投递。

OpenCode Provider 必须包含 Gemini 工具回执附件保留修复：Core 将外部事件投递为工具回执，旧版转换只发送回执文字，即使 World 已提供 `blobs`，生成请求时仍会丢失媒体。仅更新本扩展不能修复 Provider 内部的这一步。

当前 Provider 接受视频的实际 MIME 时，直接将视频作为事件附件交给 Core，不抽帧，也不需要 ffmpeg。只有 Provider 不接受视频时才走下面的抽帧流程。微信文件通道收到的 `.mp4`、`.mov` 等视频同样处理。

视频抽帧要 ffmpeg，但扩展不把它打进包里，**也绝不悄悄下载**。

### 装 ffmpeg

在「连接与工具」的 FFmpeg 区域点「下载」才会联网。

- 从 `ffmpeg-static` 的 GitHub Releases 下静态构建：压缩包约 27 MB，解压后约 77 MB。
- 装在 `<dataDir>/wechat-claw/bin/`，**不改系统 PATH**——悄悄改全局环境变量会影响其他程序，卸载扩展后还会留下垃圾。
  想手动加 PATH 的话，面板上有「复制路径」。
- 下载完跑一次 `ffmpeg -version` 才算成功，跑不通就删掉并如实报告，不靠文件名或大小猜。
- 面板能看进度、取消、删除已下载的那份。

### 用哪一份

`ffmpegSource` 决定：

- `auto`（默认）：先找系统 PATH，找不到就用面板装的那份。
- `path`：只用 PATH 里的，面板装的那份不会被使用。
- `off`：不抽帧。

### 下载走哪条网络

ffmpeg 的源在 GitHub，和微信域名不是一回事。Coopanion 注进环境变量的代理只服务模型端点，
拿它连 GitHub 会直接失败，所以下载单独配出口：`ffmpegProxyUrl` 留空表示直连，填了就那个代理。

**没有可用 ffmpeg 时不会假装看过视频**：正文会写明 `[视频帧未抽取：…]`，模型据此不去描述画面。

### 拼图而不是散图

抽出的帧会**拼成一张图**，不是发好几张。4 份图片输入变成 1 份，token 省四分之三；模型看到的也是
时间相邻的画面，更容易判断「中间发生了什么变化」。

布局按帧数和视频方向自动推导：

| 视频方向 | 4 帧 | 6 帧 | 9 帧 |
|---|---|---|---|
| 横屏 | 2×2 田字格 | 3×2 | 3×3 |
| 竖屏 | 4×1 横排 | 6×1 | 9×1 |

正文会写明顺序（例如「2列×2行，从左上到右下按时间顺序」）、原视频分辨率、每格实际尺寸——
模型据此知道画面被压到多小、细节还剩多少。

**帧数越多代价越大**：ffmpeg 解码与拼接更慢（9 帧明显比 4 帧慢），每格画面也被压得越小、细节丢得越多。
4 帧够看清「视频在讲什么」，想追踪连续动作才往上加。上限 9 帧。

## 图片与视频的投递闸门

上游 Provider 对图片有硬限制（DeepSeek：单边 ≤8192、单图 ≤32 MB、连续 ≤15 张）。
超过就整条请求被拒，用户看到的是 HTTP 400 和「发送了不支持的图片」。所以这里在交给模型之前先拦一道。

安全线比上游更严：**16 MB / 4096 像素 / 单次 10 张**。

| 情况 | 处理 |
|---|---|
| 都在范围内 | 原样附上 |
| 超限且**已装 ffmpeg** | 缩到最长边 4096，再按 JPEG 质量 3→6→9 逐级降质，每级重查体积 |
| 超限且**没装 ffmpeg** | 不附 |
| 压不下去 | 不附 |
| 超出数量额度 | 不附 |

**丢弃一定说明原因**，绝不静默吞掉——否则用户会以为消息丢了：

```
[图片未附：体积 23.4 MB，超过 16 MB 上限]
[图片未附：尺寸 8192×6144，最长边超过 4096 像素]
[图片未附：超出本次投递 10 张的上限，这是第 11 张]
[图片未附：体积 23.4 MB，超过 16 MB 上限，且没有 ffmpeg 可压缩]
[图片未附：尺寸 6000×4000，最长边超过 4096 像素，压缩后仍超标]
```

压成功了也会写：`[图片 尺寸 6000×4000，最长边超过 4096 像素，已压缩为 284 KB]`。

数量额度**一次事件投递里累计**，图片消息和视频拼图一起算。

## 网络

Coopanion 启动 Core 时会把系统代理写进 `HTTP_PROXY`/`HTTPS_PROXY`，那条代理是给模型端点用的。
微信域名走同一条代理时常常连不上，表现为 `UND_ERR_CONNECT_TIMEOUT`。

三种出口：

- `inherit`（默认）：跟随 Coopanion 的代理。
- `direct`：扩展自己建直连，绕过代理；适合代理只给模型用的情况。
- `proxy`：用 `proxyUrl` 指定的代理；适合必须走代理才能访问腾讯域名的情况。

网络设置在「配置」的「微信网络」中，修改后需重启 World。`wechat_status` 会显示当前生效的出口。

## 媒体怎么走

出站（Coo 发图/发文件）：**先过路径边界**（只许工作区）→ 读本地文件 → 申请上传参数（明文大小与 MD5）→
AES-128-ECB 加密 → POST 密文到微信 CDN → 从响应头 `x-encrypted-param` 取下载参数 → 发一条图片或文件消息。
说明文字作为独立文本消息先发，与官方发送端一致。

入站（对方发图/发文件）：用 `media.aes_key`（或图片的 `aeskey` 明文十六进制）解密 →
落到 `<工作区>/wechat-inbox/{images,files,videos,voices}/`（原文名 + 时间戳）→ 路径写进事件正文 →
模型接受该 MIME 时字节作为附件随事件到达。

能力查询使用 WorldHost 的 `modelFacts.accepts(mime)`，每条消息读取当前 Provider，不按模型名字猜能力。文件通道里的图片、音乐、视频和 Provider 接受的文档也会附上。图片仍经过体积、尺寸和数量限制，语音按落盘后的实际 MIME 判断是否附上。不支持的编码或文件、读取失败与图片超限都会取消该附件，并把原因写进正文供桌宠告知用户。

附件由 Core 和 Provider 转成上游请求。Provider 的 MIME 声明与请求实现必须同时支持该格式；上游拒绝请求时由 Core 显示具体错误，World 不在后台另发模型请求或重试。仅上游模型增加能力、Provider 仍声明只收图片时，原生音视频不会启用。

## 最近消息与收信延迟

最近消息徽章按部署时区显示，例如 `11/16 16:37`。时间保存在部署数据目录的 `wechat-claw/status.json`，重启后恢复；旧版没有该文件时从当前绑定用户的归档事件恢复。解绑会清除状态。

长轮询的 35 秒是请求等待上限，有消息时由服务端提前返回。默认「合并后投递」由 Core 的 `batching` 配置控制，本地 Cortico 默认静默等待 2.5 秒，连续收到消息时合批最长等待 15 秒。可在配置页的「微信消息投递方式」下拉框修改，保存后无需重启 World。

「图片等待补充说明」是独立设置，默认 `0` 秒（关闭）。例如设成 `2` 秒后，只有纯图片消息先等，窗口内收到紧接的文字就把图片和说明一起投递；到期只投递图片。语音、文件或斜杠指令会先放行待投图片，再按正常路径处理。图片组使用你选中的投递方式，包括 `preempt`、`interrupt` 和默认的 `debounce`；文字单发时没有这层等待。

在绑定的微信私聊里发送 `/状态`（或 `/status`）可查看通道耗时和桌宠当前阶段；`/echo 内容` 会一并回显。指令不调用模型，与正常回复共用额度。默认关闭的「试用微信任务进度卡」只为微信触发的较长工具任务尝试发送一组通用进度，不转发工具名称、参数或结果。卡片显示以手机端为准，额度不足时跳过。

微信消息实际进入桌宠处理后，等待模型或执行工具时会每隔约 5 秒续发「对方正在输入」。回复发完、任务失败、被打断或本轮结束时停止。两分钟没有观察到新的运行阶段或工具变化时也会关闭；提示能辅助判断扩展是否仍在维持本轮，不能单凭它判断模型是否卡住。

微信引用按绑定账户和会话查找。扩展先用本地索引（最多 500 条、保留 30 天），未命中时从 Core 最近 500 条同会话事件恢复归档文字和附件。引用自带微信 CDN 下载参数时也可以取回。引用附件遵循当前接收设置、体积限制与 Provider 能力，`wechat_status.lastInboundAttachments` 中用 `quoted: true` 标记。无法附入时，已保存的文件仍可按正文里的路径读取。微信只给 ID 且没有可用历史时，正文会提示无法还原。

| 投递方式 | 配置值 | 行为 |
|---|---|---|
| 合并后投递（默认） | `debounce` | 短暂等待，将连续消息合成一批 |
| 立即投递 | `flush` | 立即放行积压，当前轮继续运行 |
| 抢占尚未输出的回复 | `preempt` | 立即投递，可取消尚无外部输出且未在执行工具的模型轮 |
| 打断当前轮 | `interrupt` | 立即投递并停止当前轮，已发出的回复保留 |
| 随下一批投递 | `piggyback` | 消息入队，等其他事件唤醒 |

媒体下载、压缩和视频抽帧在入站处理里依次执行，处理结束后才继续轮询，较大媒体会拖慢后续消息。原生视频路径跳过抽帧，减少这部分处理。`wechat_status.lastInboundTiming`、事件 `meta.timing` 与「微信入站消息已处理」日志分别提供：

- `receivedAt`：这一批长轮询响应到达本机的时间。
- `receiveDelayMs`：微信消息时间到响应到达的差值，包括服务端、网络与上一次轮询前的等待；两端时钟偏差也会影响它。
- `queueMs`：同一批消息在本地开始处理前的排队时间。
- `processingMs`：保存状态、下载和准备附件所用的时间，不含 Core 合批与模型响应。

排查微信听写消息时，先查看「收到 N 条微信消息」。异常结构会额外输出「未识别的微信入站结构」，包含跳过原因、类型、已知字段的数据形状和未知字段数量。日志省略消息正文、账号、下载引用和令牌。枚举缺失或未知时，会尝试从已有 `text_item.text` 或 `voice_item.text` 读取文字。

正文里的图片尺寸读自落盘文件本身（JPEG 的 SOF 段、PNG 的 IHDR 等）。微信消息里的
`thumb_width` / `thumb_height` 是缩略图尺寸，普遍只有 210 像素宽，和真图差一个数量级，
所以不用它。

## 限制

- 只支持 1v1 私聊；没有群聊、好友列表、朋友圈、转账或红包。
- 只能回复，不能主动发起会话。回复需要对方最近一条消息的 `context_token`，约 24 小时后失效。
- **只能发工作区里的文件**。要发外面的素材，先把目录写进 `sendExtraDirs`，或把文件复制进工作区。
- 单条文本上限 4000 字；更长的回复由扩展自动分条，断行优先落在段落与句号上。
- 微信 SILK v3 语音通过 `silk-wasm` 转成 24 kHz、16-bit、单声道 WAV，无需 ffmpeg。解码失败或 WAV 超过单条媒体上限时，保存原始 `.silk`。转写来自微信的 `voice_item.text`，Provider 接受落盘音频的 MIME 时一并附上。
- Provider 不接受原生视频时，抽帧需要 ffmpeg；没有可用 ffmpeg 时不抽帧，正文会写明。不做本地音频转写。
- 微信 ClawBot 是腾讯面向 OpenClaw 的官方通道，不是面向任意第三方 agent 的公开 SDK。条款、灰度范围、额度与接口都可能变化；发布前请核对当前条款。这个扩展不是腾讯或 Coopanion 的官方扩展。
